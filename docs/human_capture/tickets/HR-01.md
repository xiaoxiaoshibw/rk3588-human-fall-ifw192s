# HR-01 — PC 侧 fetch.py：轮询拉取板端 ready 会话

> 位置：PC 顶级目录 `pc_apps/human_replay/`，与板端 `src/human_capture/` 平级。
> 数据源：板端 capture_server（`/api/v1/sessions`，无鉴权，CORS *）。
> PC 盘：`D:\Code\ldiar\captures\remote\<sid>\{meta.json,points.bin}`（D1 冻结）。
> 链路：百兆 eth1 → `scp -l 70000 ≈ 70Mbit/s`，给实时预览留 30%（README §6）。

## 范围（做什么）

- `pc_apps/human_replay/config.py`：常量（板基 URL、SSH alias、落盘根、限速、超时、slack 阈值），共享给 HR-02..05。
- `pc_apps/human_replay/fetch.py`：主循环 + 每会话一次性传输函数。
  - 每轮：GET /api/v1/sessions → 挑 `state==ready && download_requested && !transferred`
  - PATCH `state=transferring`（server 状态机硬约束；409=被抢，404=被删）
  - `ssh du -cb` 预取两文件总大小，查 PC 盘余量（需 `size + 256MB` slack）
  - scp `-l` 限速逐文件拉到 `meta.json.part` / `points.bin.part`，单文件失败即清 .part
  - 逐文件 rename、meta parse、`_validate_meta` 静态契约、`_sha256_of_points` 按 frame 实际点区校验
  - 成功后一次性 PATCH `{state: transferred, extra: {transferred: true}}`
  - 所有失败 → 清 .part + PATCH `state=ready + error=hr01:...`
- `pc_apps/human_replay/fetch_lib_test.py`：stdlib unittest，纯逻辑可控（pick/validate/hash）。

## 不做什么（防漂移）

- **不写板端代码**：只消费 capture_server REST。
- 不下载 `.bag` / `.manifest.json`（bag 是源料，正式产物是 meta+bin）。
- 不解压、不建数据库、不写 history（PC 目录树本身就是追溯索引）。
- 不重传终态会话（transferred=true 仅过滤条件；早期数据如需重拿，人工清板端 extra.transferred）。
- 不改 sessions.json 对象本身的完整 list（只走 PATCH 白名单）。

## 板上环境连带动作（交付前已做）

- `docker exec ... ln -sfn /mnt/captures/captures_remote /root/catkin_ws/captures_remote`：
  sessions.json 里字面写的是**容器内**路径（/root/catkin_ws/captures_remote/…），
  但 scp 走宿主 sshd 看不到容器内部。容器内建 symlink 桥到 SSD，
  板上旧会话无需重抽取也能被 fetch 识别。
- `cap_20261002_165321` 曾因 transfer 中断卡在 transferring，已 PATCH 回 ready 并修正其登记路径。
