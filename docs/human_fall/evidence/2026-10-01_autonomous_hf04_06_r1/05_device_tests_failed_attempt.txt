These attempts did not modify the board; they failed on the Windows ->
SSH -> bash transfer. Kept (not deleted) so the CR/quoting failures are
auditable. The successful round-1 run is `05_device_tests.txt`.

sha256sum: src/human_fall_detection/core/lidar_candidates.py: No such file or directory

Root cause: `subprocess.run(..., input=remote, text=True)` on Windows translated
`\n` to `\r\n` on the piped stdin, so the remote `bash -s` saw CR characters.
Caller also hit a GBK decode error when reading the SSH output.

Fix: pass `input=remote.encode("utf-8")` (no text mode) and decode stdout/stderr
as UTF-8 with errors="replace". Also strip `\r` locally. See the round-2 runner
`../2026-10-01_autonomous_hf04_06_r2/run_device_check.py`.

The first failed attempt also exposed a driver-side `UnicodeDecodeError` when
capturing stdout under the default GBK codec; the same fix resolves it. No board
state, driver, network or bag was touched by these attempts.
