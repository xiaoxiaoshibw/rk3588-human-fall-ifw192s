# 单目标识别开发计划

日期：2026-10-18。规则以 `PROJECT_WORKFLOW.md` 为准。本文件规划下一轮实现，本轮不改变算法行为。

## 目标与范围

先跑通“已有原始会话 → 在线等价的逐帧前景/候选 → 自动获取一个目标 → 连续跟踪 → 遮挡恢复/丢失重获 → 页面显示同一目标”。单目标表示最多维护一个活动目标；遇到多个难以区分的候选允许等待，不自动挑最大簇充当人。

首版交付的是**自动单目标几何感知链路**。人体语义识别是另一个效果问题：没有独立真值时，人体 precision/recall、误锁率、身份切换率均为 UNKNOWN，不能把候选锁定数或框稳定度当作识人准确率。人工标注不是开发前提。

优先复用 stdlib + NumPy 的现有模块。先做离线实现与生产核心接线；板端部署、现场采集、训练、下载权重不属于本计划的自动执行范围。区域分支/关节研究和跌倒确认不阻塞单目标主链。

## 已核实的起点

- 生产 `core/lidar_candidates.py` 已有点云候选、来源索引、地面相对几何和显式空场背景；候选语义为 unknown。
- `core/tracking.py` 已有距离关联、歧义拒绝、预测/实测区分和超时；当前接口围绕操作员选择设计。
- `core/node_runtime.py::FallNodeCore` 组合候选、选择、基线、跟踪和跌倒，是生产接入点；`core/pipeline.py` 的 auto_select 标为 fixture-only，不直接升级为产品策略。
- `current/run.py` 固定会话 `cap_20261018_110029`、RAW ROI 和历史 `FOREGROUND_LEDGER.npz`，尚不是原始数据自动找人的完整入口。
- `current/project_fall.py` 首个候选出现即 select，lost 后重建 ID；缺少持续性获取门和多候选竞争处理。
- 页面 `server.py::body_component` 用最大连通簇计算主体框（仅显示），`run.py` 却将全部保留前景交给区域、跟踪/跌倒；显示和计算的点集尚未统一。
- 现有 386 帧是已反复使用的开发数据，不能充当独立测试集；目前 confirmed 关闭。

## 开发顺序

| 顺序 | 改动与落点 | 可运行的完成条件 |
| --- | --- | --- |
| 1. 统一目标点集 | 在 `current` 处理链中提取共享的连通簇/来源行选择；页面只渲染运行结果。保留全部前景、各簇及排除原因；区域、包围框、候选特征使用明确绑定的同一目标点集 | 每帧可由来源行重建目标；框包围这些点；各消费者绑定相同。与 run_04 逐帧比较点数、中心、框、跟踪和姿态变化，解释差异 |
| 2. 自动获取与重获 | 最小新增 `core/target_acquisition.py`（拟定），复用 TargetTracker 关联；由当前回放先调用。质量门 + 时间持续性 + 唯一性确认后获取；持续运行中只按关联更新 | 无点击可从 searching 到 locked；空场/坏帧不锁；两个相近合格候选不强选；短遮挡不换 ID；超时重获分配新 ID、清空旧姿态基线和动作历史 |
| 3. 去除会话前景依赖 | 给当前入口增加会话/地面/显式背景/搜索区参数；用原始帧在线等价地生成候选，优先复用 `build_snapshot`。冻结账本只作旧结果对照；检查其生成过程，禁止将未来帧统计或事后选区带入自动路径 | 自动路径断开历史前景账本仍可完整运行；同一帧的输出不因追加未来帧改变；在合法搜索区内移动的合成目标可获取；已有真实会话全帧有明确结果或拒绝原因 |
| 4. 接生产核心与页面 | `FallNodeCore` 与 `ReplayPipeline` 调同一获取策略；自动模式成为此开发路径默认，保留人工选择作为可选兼容入口。自动获取来源不伪装成 operator_select；WebUI/console 显示 searching/acquiring/locked/occluded/ambiguous/lost 及原因 | 无浏览器选人请求也可经生产核心离线跑通；页面框、ID、点集、状态与核心输出一致；自动模式失锁无需人工重新点选；旧手动路径回归通过 |
| 5. 固化回归与运行证据 | 对已有可读会话做只读盘点，补充可用的静止/进出/遮挡场景；缺少的场景用明确标注的合成输入验证软件行为 | 同输入重复回放逐帧结果一致；输出运行参数、输入/源码 SHA、逐帧账本、状态转换和耗时。真实场景缺失明确列出，合成通过不替代现场效果 |

第 1→2 步先在已有前景条件下验证目标生命周期；第 3 步才证明原始数据到目标的自动链路。不能用第 2 步的成功宣称第 3 步已经完成。

## 自动获取策略的首版约束

1. 搜索区是传感器有效工作范围配置，不是围绕已知人的事后小框。候选保留原始点索引及坐标/地面版本。
2. 初次获取要求候选具备有效支撑、合理空间范围、跨帧连续性和唯一性。使用连续时间并限制帧间最大间隔，避免坏帧和断流累积“稳定”。初始窗口可试 0.6 秒且至少 5 帧，仅作可调工程起点，依据回放比较后确定，不作识人保证。
3. 不强制“必须移动”或“必须站立”作为唯一入口，以免排除静止人和低姿态。尺寸/PCA 只能提供几何证据，桌椅仍可能混淆；输出保留 semantic=unknown 和拒绝原因。
4. 初次获取与已锁目标保持分开：姿态变低/变宽不能直接判为换人；沿用实测关联并检查候选分裂/粘连歧义。
5. 短遮挡只保留明确标记的预测框/位置，不能当作实际目标点、区域节点或跌倒观测；长丢失后重新竞争获取，分配新 ID，不宣称跨丢失身份一致。
6. 时间回退、epoch/地面标定变化、数据过期、坐标不匹配时清空获取累计与旧基线；恢复后重新获取。歧义必须有退回搜索的自动路径，不能永久停在 ambiguous 等待人工。
7. 状态与输出字段尽量复用现有契约；获取过程附 acquisition 状态/原因即可，不为页面随意重写已有 track 状态枚举。自动模式下处理 requires_reselection 的兼容语义，不能仅隐藏 UI 提示。

## 验证与证据

每个实现增量：相关 `python -B -W error -m unittest ...` + 一次完整离线回放；触及页面再跑对应 JS/console 测试和页面/API 一致性检查。生产核心的离线端到端与实际板端运行分别记录。

回归至少覆盖：空场、单候选进入/离开、静止目标、两个竞争候选、噪点大簇、分裂/粘连、短遮挡、长丢失重获、低姿态、无效时间、标定切换。合成场景只验证已知输入下的软件行为；真实帧逐帧保留 candidate_id / track_id / source_rows / observed-or-predicted / acquisition_reason / binding versions。

软件完成标准：最多一个活动目标；无需选人请求；拒绝有原因；显示与计算点集一致；预测不充当观测；丢失与标定变更不继承旧基线；可重复回放。报告首次锁定时间、状态计数、重获次数和耗时分布；这些是运行描述，不是人体效果指标。实时性能门槛应根据实测帧间隔和目标板测量确定，PC 耗时不代替板端性能。

机器产物只放 `docs/evidence/<date>_<topic>/`，追加 `PROGRESS.md`、更新 `PROJECT_STATE.md`。历史证据、原始 data/junction 和冻结配置不改。需要新几何阈值时新增明确命名的变体。
