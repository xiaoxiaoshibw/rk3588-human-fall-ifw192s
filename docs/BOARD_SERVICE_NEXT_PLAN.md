# 板端服务与Qt直连的下一步计划

2026-10-27。目标：板端服务独立持续处理 `/innolidar_points`，通过现有Foxglove连接提供同源目标、高度、报警证据和失效状态；Qt连接服务即可使用，不负责算法进程的启动、地面计算或报警决策。

## 当前起点

- 本地代码中的 `single_target_node.py` 包装原 `human_fall_node` 与区域处理；`range_image_node.py` 是独立的距离图发布旁路。源码入口存在不等于当前板端已运行该版本，当前板端进程、发布者和release SHA尚待只读核实。
- 新地面/跟踪/低位链在PC `live_engine.py/live_bridge.py` 完成了一轮45秒验证；没有部署到板端。源432/算法417，103帧竞争、15帧覆盖；现场高度链已工作，真实跌倒效果UNKNOWN。最终重复解码、失效epoch与Qt探针修复仅做了后续离线验证。
- Qt默认连接 `ws://192.168.31.58:8765`，消费原始 `/innolidar_points` 与 `/single_target_live/state`。新版扩展目前放在 `local_range` 字段，Qt还支持旧消息；旧服务可连接不代表新版地面/高度/报警能力存在。
- 板端约束为Python 3.8.10、NumPy 1.17.4、stdlib；PC WebSocket桥、`asyncio.to_thread`、PC进程池封装与Qt/C#组件不能直接作为板端实现复制过去。

## 1. 核实实际板端服务与接口

先只读检查当前release/current指向、进程命令、实际入口、有效配置和源码SHA；核对原始云、状态、事件与距离图的发布者、话题、header、频率及失效心跳。区分驱动有数据、算法收到数据、算法有新结果、Qt收到结果四种状态。

输出一个可追溯的运行清单：服务版本、启动归属、输入/输出、坐标/标定、现场配置以及可用能力。没有现场状态证据的项目保留UNKNOWN。检查订阅回调沉默与重建逻辑是否已在当前release生效，避免再次把旧服务问题归到Qt。

## 2. 将同一计算核心接入板端ROS服务

复用 `ScanGrid → RangeRuntime → 共享特征/动态状态机/低位观察器`。ROS层只做消息适配、有界最新任务槽、时钟/来源检查、发布和心跳，不再形成另一套选目标或高度算法。先以同输入离线/消息替身验证新入口，再准备发布包。

- 复用现有ROS订阅、订阅健康监视与发布基础设施；确定由一个明确的服务发布规范状态话题，不能让新旧实现同时发布到 `/single_target_live/state`。
- 把PC文件中可共享的地面拟合、质量、绑定和失效规则收敛到板端可用模块。原地面选择及估计器仍保持唯一口径，不复制修改出另一套算法，也不继承“离线显示通过即物理有效”的推断。
- 背景与地面由服务持有并检查适用性。服务重启、安装/标定变化、源epoch变化分别处理；普通传输重连不无理由重学背景。现有PC RAM背景和地面不得改sid/改声明后直接作为板端新证据；跨入口复用须证明同源绑定，不能证明时重新拟合或明确不可用。有人场景不自动当空场。
- 拟合和辅助部位处理不阻塞主目标与报警；当前帧只使用此前已生效的地面。每个源帧只解码一次。缺地面仍可报告几何目标，但高度/相关报警必须不可用。

这一阶段交付板端可运行入口、共享核心和本地验证结果，不把复制PC桥或启动另一个本机后台当作完成。

## 3. 对齐服务输出与Qt消费

继续使用现有Foxglove入口及明确的状态话题，优先兼容已验证消息，避免为接线另造网络服务。保留原始云与结果的独立发送，但用同一源header和指纹关联。

状态应包含：运行/release/协议版本及能力、来源header与指纹、epoch、目标ID和实测来源行、当前地面版本/状态/原因、相对高度、姿态与下降证据、动态状态、独立低位提示、更新时间/有效期和处理统计。字段是否已有、哪些需要扩展，以实际生产者/消费者代码核对后落地，不凭文档声明视为已实现。

重点验证ROS回调消息到Foxglove原始消息的指纹一致性，不能用重打包行的SHA冒充原消息SHA。距离图与目标必须来自同一源帧；辅助结果晚到不得改写下一帧。旧协议或缺少新版能力时Qt明确显示原因。

Qt只需连接配置、兼容解析、同源校验和显示。它不重新选人、不补算报警、不保持过期结果；断流、服务重启、换代际和无地面都要真实清理。先交付“服务可连接、能力可识别、当前结果可显示和失效可解释”，不等真实跌倒精度证明后才让接口可用。

## 4. 修复影响报警的连续性与处理尾部

针对已有103帧竞争和15帧覆盖，按候选成员、分裂/粘连、关联、选择和队列耗时定位，先找最早造成错误的环节，不固定ID或放宽所有阈值。

- 真正换目标清空高度峰值、下降和报警历史；有依据的同目标短缺测只暂停合适的证据，缺测期间不增加持续时间、不显示有效报警。不因其它组件歧义无故清已选目标。
- ID重建只有在唯一几何关联与来源证据足够时才能考虑动作连续性；证据不足继续拒绝，不能跨多候选拼跌倒过程。`ground_alert_gap_v2` 继续作命名对照，采用前解释同输入差异，不直接提升为默认。
- 复用原动态状态机，把持续低位、实测下降、躺倒几何和确认资格分开。蹲/坐地、弯腰、初始低位、局部可见、遮挡、离场和断流分别覆盖；无人体/跌倒GT不输出准确率/召回率，confirmed保持关闭。
- 板端实测回调、解码、前景、跟踪、地面监视、规则、图像编码和发布耗时。优先保障主链；辅助预览/部位可以限频或缺失，但要保留同源与年龄标记。不能靠排队累积或隐瞒覆盖维持表面帧率。

这一阶段与接口接入连续推进，已经解释清楚的修复立即回到完整链路验证，不把所有可靠性问题都留到部署之后。

## 5. 回归、发布准备与实际服务验证

本地先完成Python `-B -W error` 相关测试、386/780全帧同输入对照，以及原始消息→ROS入口→Foxglove消息替身→Qt渲染。测试地面缺失/有效/失配、坏输入、目标切换、短空洞、epoch变化、订阅沉默、进程重启和断连。核对源行、高度、状态、触发源时间和所有行为变化。

准备不可变发布包、完整依赖清单、有效配置、release SHA及原有回滚路径；验证包内入口与仓库一致，板端Python/NumPy兼容性由相应运行环境证实。原有部署控制器还管理capture与页面，必须先检查并准备仅更新识别服务的最小路径，避免顺带启停采集或其他服务。

计划包含后续板端发布，但本次“制定计划”不执行部署、activate、服务启停或新一轮真实接流；这些仍遵守项目要求的明确操作授权。获得相应授权后，只更新识别服务，保留现有release和回滚，驱动/网络/采集不动。

实际验证先在Qt启动前完成构建，再进行一次明确时长的服务链检查，到期停止检查订阅，不自动无限续测。板端服务生命周期与Qt窗口生命周期分开：关闭或重新打开Qt，不应触发算法重新学习或重启；这是后续常驻服务验证的必要行为，不用本机桥代替。

分别记录源接收、算法处理、实测目标、地面有效、状态发布、Qt发布/ACK、源跳号、槽覆盖、队列年龄、处理耗时和Qt拷贝耗时。实际显示延迟必须有相应时钟/呈现证据，不能拿ACK替代。真实低位提示和动态疑似分别计数；没有触发场景就写未覆盖，不要求危险跌倒动作。

## 本轮结束后的预期使用方式

板端按部署配置独立运行；用户打开Qt，连接板端既有地址，即可看到当前目标、距离图、地面/高度状态以及报警证据或具体不可用原因。协议和运行版本可核对，失效不会保留旧报警。

“服务与界面可用”和“跌倒效果已验证”分别交付。下一轮首先执行第1步并落实第2、3步所需的软件改动；不再以修改Qt启动脚本作为服务集成的主线。每轮代码变更后完成相关测试和离线/端到端，记录进度与新机器证据，不设置人工标注、复审或逐步确认流程。
