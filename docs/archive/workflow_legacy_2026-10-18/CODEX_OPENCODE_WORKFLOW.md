## 1. 职责与授权

| 角色 | 职责 |
|---|---|
| 用户 | 指定要处理的工单、目标与例外边界；需要现场数据、业务选择或新增操作授权时提供决定 |
| Codex | 检查前置条件、准备明确工单、调用 CLI、跟进执行、读取源码与证据、独立复审、派发范围内返工、更新状态并报告最终结论 |
| OpenCode | 按工单实现、测试与取得已授权证据，写入 SUBMITTED/BLOCKED 回传；不得自行 ACCEPTED 或扩大范围 |

一张工单只有一个代码写入者。OpenCode 执行时 Codex 读取进展，待其停止后才做会修改文件的测试和审查文档更新。不并行启动第二个实现会话；不与现有人工 OpenCode 会话争用同一工作树。

收到单个工单只授权该工单及必要返工，不自动进入下一张工单。用户明确授权一组工单时，才可在各自依赖验收后顺序处理。当前 HF-03 未放行的边界继续有效。

## 2. 派工前检查

1. 读取用户工单及最新 AGENTS.md、CLAUDE.md、DISPATCH.md、CONTRACT.md、REVIEW_LOG.md、相关回传；读取 ponytail 技能。以当前文件为准，不只看历史聊天。
2. 核对工单前置状态，区分待修软件、已闭合项与设备阻塞。实际缺少的厂商证据或现场条件继续 BLOCKED；不要求实现者猜测。
3. 记录 branch/HEAD、工作树、相关文件哈希和已有差异；未跟踪文件也在基线范围内，不能仅靠 git diff 判断修改来源。保留用户改动、冻结资产、旧录制与历史回传。
4. 核对 CLI 版本、可用模型和是否有该工单的活动执行会话。当前已只读核验 OpenCode 1.18.33，`opencode run --help` 支持 `--dir/--model/--file/--format/--session`，模型列表含 `opencode-go/deepseek-v4.1-flash`。后续派工时按实际环境重新核对；不擅自换模型、升级 CLI 或改全局配置。
5. 准备派工文本：工单号/轮次、目标、允许修改路径、必须保留的行为、验收命令、证据及回传路径、设备授权范围与停止条件。例行实现取舍由 Codex/OpenCode 在已有授权内解决。

## 3. CLI 派发与记录

优先使用本机 `opencode run`，从 `D:\Code\ldiar` 运行并显式指定工作目录和模型。使用 `--file` 附加工单与共同要求，或传入明确要求读取这些本地文件的简短派工文本；避免把长正文拼进 shell。以当前 CLI help 和命令参数规则为准，不直接复制未经核对的命令。

- 首轮新建该工单会话；记录 CLI 实际返回的 session ID。
- 返工使用同一工单记录的 `--session <id>`；不用 `--continue` 猜测“最后一个会话”。用户提供既有会话时，先核对会话归属再接续。
- 使用 `--format json` 保留事件输出，stdout/stderr、实际命令和进程退出码均落盘。记录会话真正使用的模型；仅指定参数不代表模型调用已成功。
- 沿用已配置权限，在任务范围内继续操作；不以全局权限放开代替范围控制。不默认启用 `--auto`、`--share`，不把原始人体数据或凭据作为附件。
- 每轮使用新的证据目录，例如 `evidence/<日期>_<工单>_r<轮次>/`；在目录内记录派工文本、session ID、开始/结束时间、命令、退出码、相关源文件哈希与回传索引。首个任务启动时再创建运行记录，不预填成功或 session ID。

调用 CLI 只是派工，不等于完成或验收；退出码 0 也不能代替完整回传与独立验证。

## 4. 执行跟进与异常恢复

Codex 保持跟进，读取进程输出和实际日志，不让用户充当转发者。向用户报告有意义的进展、阻塞或范围变化；正常工具执行期间避免长时间无更新。CLI 长任务使用可续读进程，不因一次工具等待结束就把任务当作完成。

没有新输出不等于进程卡死。先检查进程/会话状态和日志推进，再决定继续等待或恢复。CLI/API 暂时失败时，保留失败日志，核对会话和当前差异后续接原 session；不同时重启一份相同工单，不盲目重复设备命令。

出现重复失败时先定位根因、收窄返工要求和失败用例；有进展就继续，不按任意轮数强制结束。确实缺少用户决定、凭据、现场动作或可用服务时，报告具体错误、已完成部分和解除条件；不能以“需要确认”笼统中止。用户要求停止时，停止当前执行并保留可恢复信息。

## 5. 回传收取与独立复审

OpenCode 按 RETURN_TEMPLATE.md 向 `returns/HF-xx.md` 追加本轮，最终 CLI 消息列出回传文件、修改路径、证据目录、实际检查结果和未通过项。Codex 直接从共享工作区读取，不再要求用户复制回来。

Codex 对照派工前基线核查：

1. 实际修改是否在范围内，是否影响用户已有差异或冻结接口；不能只相信回传中的“未修改”声明。
2. 沿真实调用链检查实现、同类入口、边界和兼容性，独立复现核心问题；既有测试全通过不代表未覆盖路径已通过。
3. 核对源码/配置/日志对应哈希、命令与各层退出码，区分 synthetic、offline、device；适用 ROS 构建在 Linux 执行，Windows 独立 helper 检查不能当全包构建。
4. 复用仍适用的构建与数据证据；只有代码变化、失败或未解决风险需要时才扩展/重跑检查。未实际运行的项目注明 NOT_RUN。
5. 将结论写 REVIEW_LOG.md，回传仅追加审查附记，同步工单/总表/入口文档；保留每轮失败和成功证据。

## 6. 结论与返工

| 结论 | 后续动作 |
|---|---|
| ACCEPTED | Codex 已确认该工单要求及证据满足；报告验收范围与剩余限制。未获下一单授权时就到此结束 |
| REWORK | Codex 写明原编号、优先级、位置、触发、实际/预期结果和最小修复要求，续接对应 OpenCode session；不再让用户逐轮转发 |
| BLOCKED / WAIT_DEVICE | 写清具体条件与证据，已授权且不依赖该阻塞的工作继续完成；不靠合成通过升级真机结论 |

软件通过而设备条件不足时，分别记录软件通过范围和设备 BLOCKED；整体未满足要求时不写 ACCEPTED。OpenCode 的自述和退出码不决定验收，只有 Codex 独立审查可更新 ACCEPTED。

## 7. 持续有效的操作边界

工单授权覆盖必要的本地编辑、纯函数测试、已有授权设备上的隔离检查与范围内返工。默认不 commit/push、不部署或重启活动驱动、不改网络/自启/厂商库、不覆盖旧 bag、不保存凭据、不发送外部消息。需要这些动作时先完成可审查产物，再依据用户已有授权判断是否可执行；确实新增授权时说明具体动作和原因。

本流程不创建定时任务或无人跟进的后台自动派工。跨聊天继续时读取工单记录、session ID、最新回传和审查状态后恢复，不能因会话结束擅自宣布成功。
